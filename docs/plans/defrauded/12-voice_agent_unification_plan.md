# خطة تنفيذ توحيد الوكيل الصوتي

## 1. الهدف

تنفيذ صوت داخل `sanadagent-local` يكون مجرد طبقة إدخال وإخراج فوق نفس الوكيل الحالي، وليس وكيلًا مستقلًا.
المطلوب أن يعمل:

1. `AgentRunner` كحلقة الذكاء الوحيدة.
2. `LocalRuntimeOrchestrator` كطبقة تجهيز السياق والأدوات والـ permissions.
3. الصوت كـ adapter فقط، سواء كان `STT/TTS` أو `Realtime Multimodal`.
4. نفس تاريخ المحادثة، نفس قاعدة البيانات، نفس أحداث الواجهة، ونفس الأدوات.

## 2. النطاق

الخطة تشمل:

1. توحيد مسار النص والصوت داخل نفس session.
2. توحيد حفظ الرسائل والأدوات والـ metadata.
3. توحيد الأحداث المرسلة للواجهة في الوضع النصي والصوتي.
4. دعم نوعين من الصوت:
   1. `STT/TTS` التقليدي.
   2. `Realtime Multimodal` مثل Gemini Live أو OpenAI Realtime.

الخطة لا تشمل:

1. بناء وكيل صوتي منفصل.
2. إنشاء history مستقل للصوت.
3. إنشاء DB flow منفصل للصوت.
4. تكرار منطق agent loop داخل provider.

## 3. الفرق عن خطط المهام التنفيذية الأخرى

الخطط الموجودة مثل `voice01a` و`voice01b` و`voice01c` تكتب عادة بهذا الشكل:

1. الوضع الحالي.
2. الوضع المستهدف.
3. حالات الاختبار.

أما هذه الخطة فهي أعلى قليلًا من المهام الفردية، لكنها يجب أن تبقى عملية وليست نظرية. لذلك سنستخدم نفس الأسلوب تقريبًا، مع توضيح:

1. ما الذي يجب أن يبقى موحدًا.
2. ما الذي يجب ألا يحدث.
3. كيف يتصرف كل مسار صوتي داخل النظام الحالي.

## 4. العقدة المعمارية

### 3.1 الوكيل الواحد

`AgentRunner` هو المصدر الوحيد للحقيقة.  
هو المسؤول عن:

1. التاريخ.
2. context assembly.
3. memory injection.
4. tool execution.
5. persistence.
6. metrics.
7. stream events.

### 3.2 طبقة الصوت

`RealtimeVoiceProvider` و `STT/TTS` providers يجب أن تكون adapters فقط.  
ممنوع أن تمتلك هذه الطبقة:

1. session history مستقل.
2. tool registry مستقل.
3. context builder مستقل.
4. database write path مستقل.

### 3.3 مسار التوحيد

أي مدخل صوتي يجب أن ينتهي بأحد المسارين:

1. نص من `STT` يمر إلى `LocalRuntimeOrchestrator -> AgentRunner`.
2. أو أحداث realtime تُحوَّل إلى نفس العقدة التشغيلية مع إبقاء `AgentRunner` هو المنفذ الوحيد للـ tools والحفظ.

### 4.4 الواجهة الصوتية لا تقوم بالتحويل

هذه نقطة إلزامية:

1. الواجهة لا تحوّل النص إلى صوت.
2. الواجهة لا تحوّل الصوت إلى نص.
3. الواجهة لا تفرّق في سلوكها بين `STT/TTS` و `Realtime Multimodal`.
4. الواجهة فقط:
   1. تلتقط صوت الميكروفون الخام.
   2. ترسله إلى الديمون.
   3. تستقبل الصوت الناتج.
   4. تشغله للمستخدم.

أي تحويل صوتي أو نصي يجب أن يحدث في طبقة المزود أو داخل الوكيل حسب نوع المسار، وليس في الواجهة.

## 5. المخرجات المطلوبة

### 5.1 في وضع النص

يجب أن يستمر النظام كما هو:

1. رسالة المستخدم تُحفظ في نفس session.
2. الأدوات تعمل من نفس registry.
3. الرد يُبث للواجهة على شكل streaming.
4. final answer يُحفظ بنفس metadata.

### 5.2 في وضع `STT/TTS`

1. الميكروفون يُلتقط في الواجهة.
2. `STT` يحول الكلام إلى نص.
3. النص يدخل إلى نفس turn path الموجود للنص.
4. `AgentRunner` يعالج الأدوات والسياق والحفظ.
5. الرد النصي يُبث للواجهة.
6. `TTS` يحول الرد إلى صوت.
7. الواجهة تعرض النص والصوت داخل نفس المحادثة.

### 5.3 في وضع `Realtime Multimodal`

1. الصوت يدخل إلى provider realtime.
2. provider يخرج events موحدة فقط.
3. user transcription تظهر في الواجهة كرسالة مستخدم لحظية.
4. tool use / tool result تظهر بنفس نمط الوضع النصي.
5. assistant transcription تظهر كرسالة وكحدث وكصوت.
6. الحفظ النهائي يتم في نفس session ونفس history.

## 6. مراحل التنفيذ

### المرحلة 1: تثبيت العقدة المشتركة

الهدف من هذه المرحلة هو منع أي مسار صوتي من إنشاء state مستقل.

المهام:

1. اعتماد `AgentRunner` كمنفذ وحيد للرسائل.
2. اعتماد `LocalRuntimeOrchestrator` كمنفذ وحيد لتجهيز context والأدوات والـ permissions قبل كل turn.
3. تعريف contract واضح بين الصوت والوكيل:
   1. `voice_user_transcription`
   2. `voice_assistant_transcription`
   3. `voice_audio_output`
   4. `tool_use`
   5. `tool_result`
   6. `final_answer`

مخرج المرحلة:

1. لا يوجد أي كود صوتي يكتب history بنفسه.
2. لا يوجد أي provider يملك session منفصل.

### المرحلة 2: مسار `STT/TTS`

الهدف هو جعل وضع الصوت التقليدي يمر عبر نفس الوكيل الموجود.

المهام:

1. ربط `STT` بمدخل نصي واحد.
2. جعل النص الناتج يدخل إلى نفس `AgentRunner.streamMessage` أو `sendMessage`.
3. جعل الرد النصي يُمرر إلى `TTS` بعد وصوله من الوكيل.
4. توحيد أحداث الواجهة بحيث يظهر:
   1. النص الذي قاله المستخدم.
   2. النص الذي قاله الوكيل.
   3. الصوت الناتج من `TTS`.

مخرج المرحلة:

1. المستخدم يستطيع التبديل بين الكتابة والصوت داخل نفس المحادثة.
2. لا توجد محادثة صوتية منفصلة.

### المرحلة 3: مسار `Realtime Multimodal`

الهدف هو دعم Gemini Live أو OpenAI Realtime بدون أن يصبح أي منهما وكيلًا مستقلًا.

المهام:

1. إبقاء `RealtimeVoiceProvider` adapter للبروتوكول فقط.
2. توحيد mapping للأحداث القادمة من المزود إلى event surface الداخلي.
3. توجيه tool calls إلى نفس tool execution path المستخدم في `AgentRunner`.
4. إرسال user transcription وassistant transcription إلى الواجهة في الوقت الفعلي.
5. حفظ الرسائل النهائية في نفس session storage بعد انتهاء turn أو الاتصال.

مخرج المرحلة:

1. realtime provider لا يملك context.
2. realtime provider لا يملك history.
3. realtime provider لا يكتب مباشرة إلى قاعدة البيانات.

### المرحلة 4: توحيد الأحداث بين الواجهة والصوت

الهدف هو أن الواجهة ترى نفس نوع الأحداث مهما كان المصدر.

المهام:

1. توحيد user echo.
2. توحيد tool use.
3. توحيد tool result.
4. توحيد assistant streaming chunks.
5. توحيد final response.
6. إضافة voice-specific events فقط عند الحاجة:
   1. transcription live.
   2. audio output.
   3. interrupted / barge-in.

مخرج المرحلة:

1. UI layer يعرض نفس thread timeline في جميع الأوضاع.
2. الصوت يضاف كقناة إضافية، لا كجلسة جديدة.

### المرحلة 5: الحفظ والـ metadata

الهدف هو جعل كل turn صوتي يكتب في نفس قاعدة البيانات بنفس البنية.

المهام:

1. استخدام نفس `SessionManager`.
2. استخدام نفس message schema.
3. حفظ tool messages بنفس آلية الوضع النصي.
4. حفظ assistant metadata نفسها:
   1. model
   2. provider
   3. usage
   4. runtime_ms
   5. context_tokens
   6. workspace metadata

مخرج المرحلة:

1. عند فتح التاريخ لاحقًا يظهر الصوت والنص كجزء من نفس المحادثة.

### المرحلة 6: إضافة مزودات جديدة بدون تكرار

الهدف هو ضمان أن أي مزود مستقبلي لا يفرض إعادة كتابة الوكيل.

المهام:

1. تعريف interface موحد لمزودات `STT`.
2. تعريف interface موحد لمزودات `TTS`.
3. تعريف interface موحد لمزودات realtime multimodal.
4. إبقاء `AgentRunner` كما هو تقريبًا مع تمديدات بسيطة فقط عند الحاجة.

مخرج المرحلة:

1. إضافة OpenAI Realtime أو مزود محلي لاحقًا لا تتطلب إنشاء agent loop جديد.

## 7. معايير القبول

يعتبر التنفيذ ناجحًا فقط إذا تحقق الآتي:

1. نفس thread يعمل للكتابة والصوت.
2. نفس `AgentRunner` يظل المسؤول عن الأدوات والسياق.
3. نفس الحفظ في قاعدة البيانات.
4. نفس أحداث الواجهة تظهر في النص والصوت.
5. لا يوجد أي duplication لحلقة الوكيل.
6. يمكن تبديل المستخدم بين text وvoice داخل نفس المحادثة بدون فقدان الحالة.

## 8. ترتيب الأولوية

الأولوية التنفيذية تكون كالتالي:

1. تثبيت العقدة المشتركة ومنع أي state صوتي مستقل.
2. تنفيذ `STT/TTS` على نفس مسار النص.
3. توحيد realtime provider مع نفس event contract.
4. توحيد الحفظ والـ metadata.
5. تجهيز واجهة الإضافة لمزودات مستقبلية.
