# نقطة البداية للمهمة: إزالة مؤقت طلبات الأذونات وبناء Checkpoint/Resume كامل (No Timeout + Full Checkpoint/Resume)

<div dir="rtl" style="text-align: right; direction: rtl;">

* **معرف المهمة (Task ID):** `86c9w9eq7`
* **المكونات المتأثرة (Component Tags):** `sanadagent-local`, `backend`
* **الحالة (Status):** 📝 تمت صياغة البدء
* **الوقت المتوقع (Estimated Effort):** 12 إلى 18 ساعة (12-18 Hours)

---

## الوضع الحالي (Current State)
* **المؤقت التلقائي للأذونات**: عند قيام الوكيل باستدعاء أداة حساسة تتطلب موافقة المستخدم، يتم إرسال طلب موافقة (`tool_permission_request`) إلى الواجهة. 
* **المشكلة الحالية**:
  * يفرض الديمون المحلي (`sanadagent-local`) مهلة زمنية (Timeout) افتراضية على استجابة المستخدم (مثلاً 30 ثانية).
  * إذا تأخر المستخدم في مراجعة الأداة أو الموافقة عليها، تنتهي مهلة الانتظار تلقائياً ويتم رمي استثناء `TimeoutException` وتفشل الجلسة مع رفض تلقائي، مما يمنع تعليق واستئناف الجلسات بشكل مرن وغير محدود.
  * لا يوجد عقد صريح يميز بين "الطلب المعلق" و"المنعطف المعلق بالكامل"، مما يجعل الاستئناف بعد إغلاق التطبيق أو انقطاع الاتصال غير موثوق حتى لو وصلت الاستجابة لاحقاً.
  * الطلبات المعلقة مرتبطة بعمر العملية والذاكرة المؤقتة للديمون، لذلك إعادة تشغيل `sanadagent-local` تُسقط التنفيذ المعلق نفسه.
  * لا يوجد checkpoint تشغيلي يسمح باستكمال الـ tool call أو الـ turn من نفس النقطة بعد restart.

---

## الوضع المستهدف / الهدف (Target State)
* **إلغاء مهلة الانتظار بالكامل (Infinite Suspended Waiting)**:
  * إزالة أي `.timeout(...)` أو رفض تلقائي مبني على الزمن.
  * يظل المنعطف معلقاً بلا سقف زمني إلى أن يرد المستخدم.
* **Checkpoint/Resume كامل للمنعطف المعلق (Full Suspended Turn Checkpoint)**:
  * يجب أن يتحول طلب الإذن من Future عابر إلى checkpoint تشغيلي قابل للإحياء بعد restart.
  * يتم حفظ حالة المنعطف بالكامل، وليس طلب الإذن فقط: `thread_id`, `session_id`, `workspace_id`, `request_id`, `run_id`, `tool_name`, `tool_input`, `permission_class`, ومرحلة التنفيذ الحالية.
* **استئناف شفاف قبل وبعد restart (Transparent Resume Before/After Restart)**:
  * إذا أُغلق `sanad-client` أو `sanadagent-local` ثم عادا، يجب أن يرى المستخدم نفس الطلب المعلق ويستطيع الرد عليه دون تمييز بصري أو منطقي بين الحالتين.
  * بعد الرد، يستكمل `sanadagent-local` التنفيذ من نفس النقطة دون إعادة تنفيذ الخطوات السابقة بشكل مضاعف.

---

## القرار المعماري (Architecture Decision)
* **لن نعتمد حفظ قواعد الموافقة الدائمة في قاعدة البيانات فقط**:
  * أما `pending permissions` نفسها فتُخزن في `Map` داخل الذاكرة وتُستعاد فقط طالما العملية الحية ما زالت شغالة.
  * هذا لا يحقق هدفنا لأن restart للديمون عندهم يُسقط الطلب المعلق والتنفيذ المعلق.
* **المسار المعتمد في Sanad**:
  * بناء state machine صريحة للمنعطفات المعلقة.
  * بناء storage ثابت للـ checkpoints.
  * ربط الرد على الإذن بعملية resume فعلية وليس مجرد إغلاق prompt.

## نموذج الحالة المطلوب (Required Runtime State Machine)
* الحالات الأساسية:
  * `running`
  * `awaiting_permission`
  * `resuming`
  * `completed`
  * `failed`
  * `cancelled`
* يجب أن يحتوي checkpoint على:
  * هوية الجلسة والمحادثة.
  * هوية الـ run أو turn.
  * وصف الطلب المعلق.
  * موضع الاستئناف الدقيق داخل طبقة التشغيل.
  * metadata تكفي لمنع إعادة تنفيذ الخطوة السابقة مرتين.

## نطاق التنفيذ الفني (Technical Execution Scope)
### المرحلة 1: فصل تعليق الإذن عن الذاكرة المؤقتة
* إزالة مهلة الانتظار من `platform_runtime_bridge.dart` والطبقات المرتبطة.
* إيقاف الاعتماد على `Completer` وحده كمصدر الحقيقة.
* إدخال abstraction جديد مثل `SuspendedTurnStore` أو `PermissionCheckpointStore`.

### المرحلة 2: تصميم storage ثابت للـ checkpoints
* إنشاء كيان persistent واضح للمنعطف المعلق.
* الحقول الأساسية:
  * `checkpoint_id`
  * `thread_id`
  * `session_id`
  * `workspace_id`
  * `request_id`
  * `run_id`
  * `status`
  * `tool_name`
  * `tool_input`
  * `permission_payload`
  * `resume_payload`
  * `created_at`
  * `updated_at`
* تخزين الـ checkpoint في SQLite أو طبقة التخزين المعتمدة محلياً داخل `sanadagent-local`.

### المرحلة 3: بناء نقطة استئناف فعلية
* تعديل مسار تنفيذ الأدوات الحساسة بحيث عند الاصطدام بالإذن:
  * يتم إنشاء checkpoint.
  * تُحفظ كل بيانات الاستئناف.
  * يتوقف المسار عند `awaiting_permission`.
* عند وصول الرد:
  * يُحمّل checkpoint.
  * يُحدّث إلى `resuming`.
  * يُعاد حقنه في runtime ويكمل المسار من نقطة الاستئناف.

### المرحلة 4: منع التكرار وضمان idempotency
* يجب أن يكون resume آمناً إذا:
  * أُعيد تشغيل الديمون أكثر من مرة.
  * وصل الرد مرتين.
  * حاول العميل إعادة جلب الحالة أثناء الاستئناف.
* إضافة guards صريحة تمنع double execution لنفس tool call.

### المرحلة 5: عقود الاسترجاع والاستئناف
* إضافة query محلية لإرجاع جميع checkpoints بحالة `awaiting_permission`.
* إضافة command/resume contract واضح عند الرد:
  * `approve once`
  * `approve and persist policy` إذا وُجد لاحقاً
  * `deny`
  * `deny with feedback`
* هذه المهمة تبني runtime + persistence + resume contract، بينما عرض الـ UI نفسه في `sanad-client` يكتمل في `86c9w9dtk`.

## الخطوات الفعلية للتنفيذ (Concrete Implementation Steps)
1. فهرسة جميع نقاط `ensureAuthorized` و`tool_permission_request` الحالية وتحديد نقطة التعليق الوحيدة المعتمدة.
2. إنشاء model جديد للـ suspended permission checkpoint داخل `sanadagent-local`.
3. إضافة repository/storage layer لقراءة وكتابة checkpoints.
4. تعديل `PermissionManager` أو الطبقة المالكة لتُنشئ checkpoint قبل التعليق.
5. تعديل `PlatformRuntimeBridge` ليقرأ من checkpoint store بدل انتظار رد in-memory فقط.
6. بناء bootstrap عند startup يحمّل checkpoints المفتوحة ويعيد تفعيلها داخل runtime.
7. بناء resume path يعيد استكمال الـ turn من checkpoint بعد وصول الرد.
8. إضافة اختبارات restart حقيقية تؤكد أن الطلب يستمر ويُستأنف بعد إغلاق وفتح الديمون.

## شروط القبول (Definition of Done)
* أي طلب إذن حساس لا يفشل تلقائياً بسبب الزمن مهما تأخر المستخدم في الرد.
* restart لـ `sanad-client` أو `sanadagent-local` لا يُسقط الطلب ولا التنفيذ المعلق.
* بعد restart يمكن استرجاع checkpoint وresume نفس المنعطف دون إعادة تشغيل الخطوات السابقة بشكل مزدوج.
* لا يتم استئناف تنفيذ الأداة إلا بعد وصول رد صريح من المستخدم.
* لا توجد مسارات صامتة تعتبر "عدم الرد" بمثابة "رفض".
* يوجد storage ثابت يمكنه إعادة تحميل جميع checkpoints المفتوحة عند startup.
