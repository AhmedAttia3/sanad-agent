# خطة المرحلة السابعة عشر: تهيئة البنية التحتية لمصادقة الويب وموقع البوابة المستقل

## الأهداف (Goals)
تهدف هذه الخطة إلى إعادة صياغة تجربة المستخدم (UX) وجعلها أكثر مرونة وأماناً من خلال:
1. إلغاء إلزامية تسجيل الدخول لتشغيل التطبيق والوكيل محلياً (Offline Mode) بشكل كامل.
2. حماية البيانات الحساسة (Google Client ID & Secrets) بإزالتها تماماً من تطبيق الواجهة المفتوح المصدر، ونقل عملية تسجيل الدخول إلى صفحة ويب مستقلة تابعة لبوابة الاتصال (`sanad-gateway`).
3. تبسيط البدء السريع للمستخدم الجديد عن طريق التحقق التلقائي من حالة الوكيل ومزودي الخدمة، وتوجيه المستخدم لإعداد مزود الخدمة الأول (Gemini, OpenAI, إلخ) عبر شاشة تراكبية (Overlay) نظيفة.

---

## النطاق (Scope)
تركز هذه الخطة على تهيئة البنية التحتية فقط لمشروع البوابة وتجهيز نقاط اتصال جلسات المصادقة:
* **مشروع البوابة الجديد (`sanad-portal`):**
  - إنشاء مجلد جديد باسم `sanad-portal` في الجذر الرئيسي للمستودع لخدمة صفحات المصادقة وإدارة الحساب والاشتراكات مستقبلاً، ويتم تشغيله داخل حاوية Docker مستقلة ليبقى الـ `backend` مخصصاً فقط للـ REST APIs والـ WebSockets.
  - بناء صفحة تسجيل الدخول (`index.html` / `/login`) في هذا المشروع بأسلوب عصري وتحتوي على:
    - زر تسجيل الدخول بواسطة جوجل (**Google Sign-In**).
    - تهيئة وتصميم واجهة المستخدم لتستوعب التحديثات المستقبلية بسهولة (حيث سنقوم لاحقاً بإضافة تسجيل الدخول بواسطة البريد الإلكتروني وتسجيل الدخول باستخدام حساب آبل **Apple Sign-In**).
  - بناء صفحة النجاح (`success.html`) التي يتم توجيه المستخدم إليها بعد إتمام عملية تسجيل الدخول بنجاح لتأكيد اكتمال العملية وإرشاده بالعودة للتطبيق.
* **البوابة الخلفية (`backend` / `sanad-gateway`):**
  - إضافة نقاط اتصال (API Endpoints) للمصادقة وتمرير التوكن للعميل دون الحاجة لتخزين بيانات جوجل الحساسة في كود الواجهة:
    - `POST /api/auth/session/start`: يقوم العميل (سواء الهواتف أو سطح المكتب) باستدعائها عند بدء تسجيل الدخول لتوليد معرف جلسة فريد ومؤقت `session_id`.
    - `GET /api/auth/session/status`: يقوم العميل بالاستعلام الدوري (Polling) من خلالها مستخدماً الـ `session_id` و`polling_token` الخاص بالتطبيق للتحقق مما إذا كان المستخدم قد أكمل تسجيل الدخول في المتصفح بنجاح، وعند اكتماله تقوم البوابة بإرجاع توكن الدخول (`access_token`) للعميل بشكل آمن.
    - `POST /api/auth/device/start`: التدفق الأساسي للتطبيق والوكيل مفتوحي المصدر؛ يولد `device_session_id` و`polling_token` خاصين بالعميل، ويعرض للمستخدم `user_code` قصيراً لإدخاله في المتصفح.
    - `GET /api/auth/device/{provider}/login`: تختار البوابة مزود المصادقة من خلال هذا المسار دون أن يحتاج التطبيق أو الوكيل لمعرفة المزود.
    - `POST /api/auth/device/status`: يستقبل `device_session_id` و`polling_token` داخل JSON body فقط، ولا يسمح للمتصفح أو رابط البوابة باستلام التوكنات أو polling token.
  - تحديث مسارات استدعاءات Google OAuth لتوجيه عملية تبادل التوكنات وتخزينها بالجلسة النشطة تمهيداً لالتقاطها.

## معايير القبول (Acceptance Criteria)

### 1. نقاط الاتصال لجلسات المصادقة (Auth Session Endpoints)
* نجاح استدعاء `POST /api/auth/session/start` وإرجاع `session_id` صالح ومخزن في الذاكرة المؤقتة (أو قاعدة البيانات) مع وقت انتهاء صلاحية (Expiration Time).
* عند استدعاء `GET /api/auth/session/status` بـ `session_id` غير صالح أو منتهي الصلاحية، يتم إرجاع خطأ 404 أو حالة غير مكتملة، ولا يتم إرجاع التوكنات إلا عند وجود `polling_token` الصحيح.
* عند نجاح المصادقة عبر Google OAuth، يتم ربط التوكن الناتج بالـ `session_id` المقابل، وتقوم `GET /api/auth/session/status` بإرجاع `access_token` بنجاح فقط عند إرسال `polling_token` الخاص بالتطبيق وتحديث حالة الجلسة إلى مكتملة.
* يجب رفض أي Google ID token لا يطابق `aud` الخاص بمعرفات عملاء Sanad الموثوقة (`GOOGLE_CLIENT_ID` أو `GOOGLE_CLIENT_IDS`).
* يجب أن تعتمد مصادقة Socket.IO العامة على JWT صادر من الباكند فقط، دون أي صيغ mock مثل `user:<id>`.
* يجب أن تستخدم Socket.IO قائمة origins موثوقة من إعدادات الباكند، وليس wildcard مفتوحاً.
* يجب إرسال `refresh_token` داخل body الطلب وليس في query string، ويجب عدم طباعة التوكنات الخام في سجلات العميل أو الوكيل.
* يجب أن يستخدم التطبيق والوكيل تدفق device-code: يعرضان `user_code` فقط للمستخدم، يحتفظان بـ `polling_token` داخل العملية المحلية، ويرسلان الاستعلام الدوري عبر `POST /api/auth/device/status` ببيانات JSON.
* يجب أن تبقى معرفة مزود المصادقة داخل البوابة والباكند فقط؛ لا يجب أن يحتاج التطبيق أو `sanad login` لأي تعديل عند إضافة Apple أو مزود آخر.
* يجب ألا يظهر `polling_token` في URL، أو سجلات العميل، أو صفحة البوابة، أو ردود المتصفح.
* يجب ألا يستطيع `session_id` الظاهر في رابط المتصفح وحده سحب التوكنات من `/api/auth/session/status`.
* يجب تطبيق rate limits على مسارات إنشاء الجلسات، الاستعلام الدوري، تسجيل الدخول بالمزود، وOAuth callback.
* يجب تخزين device token كـ hash في قاعدة البيانات، وعدم إرجاعه في قوائم الأجهزة العادية، وإرجاعه فقط عند الإنشاء أو التدوير المقصود.

### 2. مشروع بوابة الويب المستقل (`sanad-portal`)
* إمكانية تشغيل الحاوية المستقلة `sanad-portal` عبر Docker وتصفحها محلياً.
* تحديد المنفذ الخاص بالبوابة (`PORTAL_PORT`) من خلال ملفات متغيرات البيئة (`.env.dev` و `.env.prod`) وتمريره إلى ملف `docker-compose.yml` كباقي المشاريع الأخرى في المستودع.
* احتواء صفحة `index.html` على خيار تسجيل الدخول بواسطة Google، وتهيئتها بصرياً لاستيعاب خيارات الدخول بالبريد وآبل مستقبلاً.
* عند قيام المستخدم بتسجيل الدخول بنجاح، يتم توجيهه لصفحة `success.html` وتظهر له رسالة نجاح واضحة مع إرشاد لإغلاق المتصفح والعودة للتطبيق.

## قائمة المهام (Checklist)

### المرحلة الأولى: بناء نقاط اتصال جلسات المصادقة في البوابة (Gateway/Backend)
- [x] إنشاء نقاط الاتصال الخاصة بإدارة جلسات المصادقة السريعة في البوابة (`backend`):
  - `POST /api/auth/session/start`: لإنشاء جلسة استعلام مؤقتة وإرجاع معرف الجلسة `session_id`.
  - `GET /api/auth/session/status`: لفحص حالة الجلسة وإرجاع توكن الدخول `access_token` في حال إتمام المصادقة وإرسال `polling_token` الصحيح.
  - `POST /api/auth/device/start`: لإنشاء جلسة device-code وإرجاع `user_code` للعرض و`polling_token` الخاص بالعميل.
  - `POST /api/auth/device/status`: لفحص حالة جلسة device-code باستخدام `polling_token` داخل body الطلب.
- [x] تحديث مسارات استدعاءات Google OAuth لتوجيه عملية تبادل التوكنات وتخزينها بالجلسة النشطة تمهيداً لالتقاطها.

### المرحلة الثانية: إنشاء مشروع البوابة المستقل (`sanad-portal`) وتشغيله بـ Docker
- [x] إنشاء مجلد جديد باسم `sanad-portal` في الجذر الرئيسي للمستودع.
- [x] بناء صفحات الويب باستخدام HTML/JS وتنسيق CSS مخصص وراقي:
  - صفحة تسجيل الدخول (`index.html` / `/login`): تحتوي على زر تسجيل الدخول بواسطة جوجل، ومجهزة بصرياً وهيكلياً لإضافة البريد الإلكتروني وحساب آبل لاحقاً.
  - صفحة نجاح العملية (`success.html`): تظهر للمستخدم بعد اكتمال المصادقة بنجاح وترشده لإغلاق التبويب والعودة للتطبيق.
- [x] إضافة متغير البيئة `PORTAL_PORT` إلى ملفات التكوين البيئية (`.env.dev` و `.env.prod`).
- [x] إنشاء ملف `Dockerfile` لإعداد حاوية Nginx خفيفة لخدمة المشروع بشكل مستقل وسريع.
- [x] تسجيل خدمة `sanad-portal` في ملف `docker-compose.yml` الرئيسي للمستودع، وربط منفذها عبر المتغير `${PORTAL_PORT:-8082}:80` وربطه بالشبكة المشتركة مع البوابة.
