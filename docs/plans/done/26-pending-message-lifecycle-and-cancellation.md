# خطة المرحلة السادسة والعشرين: دورة حياة الرسائل المعلقة وإلغاؤها

## 1. الملخص

تضيف هذه المرحلة عقدًا موحدًا لدورة حياة رسائل المستخدم التي لم تدخل بعد في سياق تنفيذ الوكيل. يشمل ذلك الرسائل العادية الموضوعة في طابور الجلسة (`queued`) ورسائل التوجيه المباشر التي استلمها الوكيل لكنها تنتظر نقطة تسليم آمنة بعد انتهاء الأداة أو دفعة الأدوات (`pending_steer`).

يظل الوكيل المحلي المصدر الوحيد للحقيقة. لا تستنتج واجهة Flutter أن الرسالة معلقة أو مُسلّمة اعتمادًا على حالة العرض المحلية، ولا تحذف الرسالة تفاؤليًا. يعيد الوكيل أحداث حالة صريحة تحمل `request_id` نفسه، وتعرض الواجهة الرسالة في منطقة الانتظار حتى يؤكد الوكيل تسليمها أو إلغاءها.

## 2. المشكلة الحالية

1. الرسالة العادية أثناء انشغال الجلسة تظهر في لوحة الرسائل المنتظرة، لكن لا يوجد عقد عام يصف حالتها خارج العلامة `metadata.queued`.
2. رسالة `steer` تظهر في المحادثة فور استلامها، رغم أنها قد تظل داخل ذاكرة `AgentRunner` مدة طويلة حتى تنتهي الأداة الحالية.
3. لا يستطيع المستخدم معرفة الفرق بين رسالة `steer` تم تسليمها للنموذج ورسالة لا تزال تنتظر نقطة التسليم الآمنة.
4. لا يوجد أمر موحد لإلغاء رسالة معلقة باستخدام `request_id`.
5. حذف الرسالة من الواجهة وحدها قد يعطي انطباعًا خاطئًا بالإلغاء بينما تكون الرسالة قد دخلت بالفعل إلى سياق النموذج.
6. رسائل `pending_steer` غير المسلّمة تعتمد على الذاكرة المؤقتة؛ فقدان عملية الوكيل قبل التسليم قد يفقد حالتها.

## 3. الأهداف

1. توحيد رسائل `queued` و`pending_steer` تحت نموذج دورة حياة واحد يملكه الوكيل.
2. عرض الرسائل غير المسلّمة خارج سجل المحادثة الرئيسي في لوحة انتظار موحدة.
3. توضيح سبب الانتظار للمستخدم: انتظار دور الجلسة أو انتظار انتهاء الأداة.
4. إتاحة حذف أي رسالة ما دامت في حالة قابلة للإلغاء.
5. ضمان نتيجة حتمية عند سباق الإلغاء مع التسليم.
6. إدراج الرسالة في المحادثة فقط بعد أن يؤكد الوكيل انتقالها إلى `delivered`.
7. الحفاظ على الترتيب الدلالي: نتيجة الأداة، ثم رسالة `steer`، ثم الرد المعدّل.
8. استعادة الرسائل المعلقة وحالاتها بعد إعادة الاتصال أو إعادة تشغيل الوكيل.

## 4. خارج النطاق

1. إلغاء رسالة وصلت بالفعل إلى النموذج أو التراجع عن تأثيرها بعد `delivered`.
2. إيقاف الأداة الحالية عند حذف `pending_steer`.
3. إعادة ترتيب الرسائل يدويًا بالسحب والإفلات.
4. تعديل سياسة `stop` العامة للجلسة، عدا توحيد إشعارات إلغاء الرسائل الناتجة عنها.
5. مزامنة الرسائل المعلقة بين جلسات مختلفة؛ كل رسالة تبقى مرتبطة بـ`session_id` واحد.

## 5. نموذج الحالة المستهدف

### 5.1 نوع الرسالة المعلقة

يستخدم البروتوكول الحقل `pending_kind` بالقيم التالية:

- `queue`: رسالة عادية تنتظر انتهاء الـturn الحالي وبدء دور جديد.
- `steer`: رسالة توجيه تنتظر نقطة تسليم آمنة داخل الـturn الحالي.

### 5.2 حالات دورة الحياة

- `queued`: الرسالة العادية موجودة في طابور FIFO.
- `pending_steer`: رسالة التوجيه محفوظة ولم تُحقن بعد.
- `delivering`: حالة انتقالية اختيارية تبدأ بعد حجز الرسالة للتسليم وتمنع قبول الإلغاء المتأخر.
- `delivered`: دخلت الرسالة إلى سياق الوكيل وأصبحت جزءًا من سجل المحادثة.
- `cancelling`: حالة عرض محلية مؤقتة أثناء انتظار نتيجة طلب الإلغاء؛ لا تُخزّن كمصدر حقيقة في الوكيل.
- `cancelled`: ألغى الوكيل الرسالة قبل التسليم.
- `rejected`: تعذر تنفيذ العملية المطلوبة، مع `reason` وحالة الوكيل الحالية.

### 5.3 الانتقالات المسموحة

```text
رسالة عادية أثناء الانشغال:
queued ───────────────► delivered
   └─────────────────► cancelled

رسالة توجيه مباشرة:
pending_steer ────────► delivering ───────► delivered
       └──────────────► cancelled

تحويل رسالة من الطابور إلى Steer:
queued ───────────────► pending_steer ─────► delivered
```

الحالتان `delivered` و`cancelled` نهائيتان. لا يقبل الوكيل إلغاء رسالة في `delivering` أو `delivered`، ويعيد حالتها الحالية بدل ادعاء نجاح الإلغاء.

## 6. عقد البروتوكول

### 6.1 حدث حالة موحد

إضافة حدث canonical باسم `pending_message_changed` يحمل:

```json
{
  "session_id": "session-id",
  "request_id": "request-id",
  "content": "نص الرسالة",
  "pending_kind": "queue",
  "state": "queued",
  "created_at": "ISO-8601",
  "updated_at": "ISO-8601",
  "reason": null
}
```

قواعد العقد:

1. `(session_id, request_id)` هو المفتاح الفريد للرسالة.
2. كل انتقال حالة يحمل `request_id` الأصلي ولا يولّد هوية جديدة.
3. الأحداث مكررة الوصول مسموحة، ويجب أن يكون تطبيقها idempotent.
4. لا تستطيع الواجهة الانتقال بالحالة إلى الخلف.
5. يرسل الوكيل لقطة `pending_messages` ضمن تاريخ الجلسة لإعادة الترطيب.

### 6.2 أمر الإلغاء

إضافة أمر `cancel_pending_message` بالحمولة التالية:

```json
{
  "session_id": "session-id",
  "request_id": "request-id"
}
```

النتائج الممكنة:

- نجاح: حدث `pending_message_changed` بحالة `cancelled`.
- سبق التسليم: رد بحالة `delivered` وسبب `already_delivered`.
- جارٍ التسليم: رد بحالة `delivering` وسبب `delivery_in_progress`.
- غير موجود: `rejected` وسبب `not_found`.
- جلسة غير مطابقة: `rejected` وسبب `session_mismatch`.

### 6.3 تأكيد التسليم

عند التسليم:

1. يحجز الوكيل الرسالة ذريًا وينقلها إلى `delivering`.
2. يحقن النص في نقطة التنفيذ المناسبة.
3. يحفظ سجل التسليم.
4. يصدر `user_message` مع `request_id` نفسه و`metadata.pending_state = delivered`.
5. يصدر الحالة النهائية `delivered` أو يجعل حدث المستخدم نفسه تأكيدًا نهائيًا وفق تنفيذ البروتوكول المختار.

لا تُضاف الرسالة إلى سجل المحادثة الرئيسي قبل الخطوة الرابعة.

## 7. ملكية الوكيل والتخزين

### 7.1 سجل الرسائل المعلقة

إنشاء سجل دائم على مستوى الوكيل، ويفضل جدول SQLite باسم `pending_messages`، يحتوي على:

- `request_id` كمفتاح أساسي.
- `session_id`.
- `content`.
- `pending_kind`.
- `state`.
- `created_at` و`updated_at`.
- `delivered_at` أو`cancelled_at` عند توفرهما.
- بيانات الربط الاختيارية مثل `source_request_id` عند تحويل رسالة queue إلى steer.

يجب أن تكون عمليات إنشاء الرسالة، حجزها للتسليم، وإلغائها ذرية لمنع سباق `cancel` مع `deliver`.

### 7.2 طابور الجلسة

يستمر `SessionRunOrchestrator` في امتلاك ترتيب FIFO، لكنه يزامن `_pendingEvents` مع سجل الرسائل المعلقة. عند إعادة تشغيل الوكيل يعاد بناء الطابور حسب `created_at` للرسائل ذات الحالة `queued`.

### 7.3 رسائل Steer المعلقة

يحتفظ `AgentRunner` بقائمة التشغيل السريعة داخل الذاكرة، بينما يبقى السجل الدائم في طبقة الجلسة. عند التسليم أو الإلغاء يحدّث الوكيل الذاكرة والتخزين ضمن عملية منسقة واحدة.

إضافة واجهة مثل `cancelPendingSteer(requestId)` تعيد نتيجة صريحة بدل قيمة boolean مبهمة، وتمنع حذف رسالة انتقلت إلى `delivering`.

## 8. سلوك الواجهة

### 8.1 لوحة الانتظار الموحدة

تحويل لوحة `_QueuedMessagesBox` إلى لوحة رسائل معلقة موحدة تعرض النوعين:

- رسالة Queue: شارة «في قائمة الانتظار».
- رسالة Steer: شارة «ستُرسل بعد انتهاء الأداة».
- أثناء طلب الإلغاء: شارة «جارٍ الإلغاء» مع تعطيل الأزرار.
- عند رفض الإلغاء: تعود الشارة إلى حالة الوكيل الحالية ويظهر سبب مختصر غير معطل للمحادثة.

### 8.2 الظهور في المحادثة

- لا تظهر `queued` أو`pending_steer` داخل السجل الرئيسي.
- عند `delivered` تزال من لوحة الانتظار وتدخل المحادثة بنفس `request_id`.
- رسالة Steer المسلّمة توضع بعد بطاقة الأداة المرتبطة وقبل الرد التالي.
- تحديث `tool_result` يدمج داخل بطاقة الأداة الموجودة ولا يحرّك فقاعة Steer.

### 8.3 زر الحذف

يظهر زر حذف بجوار الرسائل في `queued` و`pending_steer` فقط.

عند الضغط:

1. ترسل الواجهة `cancel_pending_message`.
2. تحتفظ بالرسالة في اللوحة وتعرض `cancelling`.
3. تزيل الرسالة فقط بعد تأكيد `cancelled` من الوكيل.
4. إذا سبق التسليم، تنتقل الرسالة إلى المحادثة ولا تعرض الواجهة نجاحًا زائفًا للحذف.

## 10. مراحل التنفيذ

### المرحلة A: نموذج الحالة والتخزين

1. تعريف `PendingMessageKind` و`PendingMessageState` ونتائج الإلغاء.
2. إضافة التخزين الدائم والفهارس اللازمة.
3. إضافة انتقالات ذرية للحجز، التسليم، والإلغاء.
4. إعادة ترطيب طوابير الجلسات عند بدء الوكيل.

### المرحلة B: بروتوكول الوكيل

1. إضافة `pending_message_changed`.
2. إضافة `cancel_pending_message`.
3. استبدال صدى `metadata.queued` المؤقت بعقد lifecycle، مع إبقاء توافق قراءة مؤقت أثناء الانتقال إن لزم.
4. إصدار تأكيد التسليم قبل تحرير قفل الجلسة.

### المرحلة C: دمج Queue وSteer

1. ربط `_pendingEvents` بسجل الرسائل المعلقة.
2. ربط `_pendingSteers` بالسجل نفسه.
3. دعم التحويل الذري من `queued` إلى `pending_steer`.
4. تنفيذ الإلغاء حسب النوع دون التأثير على الأداة أو الـturn النشط.

### المرحلة D: العميل وتجربة المستخدم

1. إضافة pending store موحد keyed by `request_id`.
2. ترطيب الحالة من `pending_messages` في تاريخ الجلسة.
3. بناء لوحة موحدة مع الشارات وزر الحذف.
4. عدم إدراج الرسالة في المحادثة قبل حدث التسليم المعتمد.
5. معالجة سباق الإلغاء والتسليم دون وميض أو رسائل مكررة.

### المرحلة E: إزالة التوافق المؤقت

بعد دعم جميع مسارات النقل المحلية والسحابية:

1. إزالة الاعتماد على `metadata.queued` كمصدر حالة مستقل.
2. إزالة أي حذف تفاؤلي متبقٍ في العميل.
3. توحيد سجل الأحداث الحية وتاريخ الجلسة على النموذج الجديد.

## 11. معايير القبول

1. عند إرسال رسالة عادية أثناء انشغال الجلسة تظهر فقط في لوحة الانتظار بحالة `queued`.
2. عند إرسال Steer أثناء أداة مدتها 30 ثانية تظهر فقط في لوحة الانتظار بحالة `pending_steer` طوال مدة الأداة.
3. بعد انتهاء الأداة تنتقل رسالة Steer إلى المحادثة بعد بطاقة الأداة وقبل الرد المعدّل.
4. يستطيع المستخدم حذف رسالة Queue قبل بدء دورها، ولا ينفذها الوكيل لاحقًا.
5. يستطيع المستخدم حذف Pending Steer قبل نقطة التسليم، ولا تدخل إلى سياق النموذج.
6. إذا تزامن الحذف مع التسليم، تعرض الواجهة النتيجة الفعلية للوكيل ولا تخفي رسالة تم تسليمها.
7. لا يمكن حذف رسالة في `delivered` أو`delivering`، ويعود سبب واضح.
8. لا تظهر علامات `OUT-OF-BAND` أو بيانات الحقن الداخلية في الواجهة أو سجل الجلسة.
9. إعادة فتح الجلسة أثناء وجود رسائل معلقة تعيد اللوحة والحالات والترتيب نفسه.
10. إعادة تشغيل الوكيل لا تفقد الرسائل `queued` أو`pending_steer`.
11. تكرار حدث lifecycle أو إعادة إرسال طلب الإلغاء لا ينتج نسخًا مكررة.
12. `stop` ينقل جميع الرسائل القابلة للإلغاء في الجلسة إلى `cancelled` ويصدر أحداثها النهائية.

## 12. خطة الاختبارات

### 12.1 اختبارات الوكيل

- Queue عادي: إنشاء، FIFO، تسليم، وإلغاء.
- Steer أثناء أداة متأخرة: يبقى `pending_steer` حتى انتهاء الأداة.
- إلغاء Steer قبل انتهاء الأداة: لا يظهر النص في طلب LLM التالي.
- سباق الإلغاء مع `_applyPendingSteerToToolResults`: نتيجة ذرية واحدة فقط.
- تحويل Queue إلى Steer مع الحفاظ على `request_id`.
- إعادة تشغيل الوكيل واستعادة الرسائل المعلقة.
- `stop` يلغي كل الرسائل القابلة للإلغاء للجلسة فقط.

### 12.2 اختبارات البروتوكول

- ترجمة جميع حالات `pending_message_changed` دون فقد الهوية أو التوقيت.
- استجابة `cancel_pending_message` لكل حالة نهائية وانتقالية.
- تاريخ الجلسة يعيد `pending_messages` منفصلة عن `messages` المسلّمة.
- النقل المحلي والسحابي ينتجان الحمولة canonical نفسها.

### 12.3 اختبارات العميل

- عدم ظهور `queued` و`pending_steer` داخل المحادثة.
- ظهور الشارة الصحيحة لكل نوع.
- حالة `cancelling` لا تحذف الصف قبل التأكيد.
- قبول `cancelled` يزيل الصف، ورفض `already_delivered` ينقل الرسالة للمحادثة.
- تحديث نتيجة الأداة لا يغيّر موضع Steer المسلّمة.
- إعادة الترطيب لا تنتج ازدواجًا بين لوحة الانتظار والمحادثة.

## 13. المخاطر والضوابط

- **سباق الإلغاء والتسليم:** يعالج بانتقال ذري إلى `delivering` قبل الحقن.
- **ازدواج أحداث الشبكة:** يعالج بتطبيق idempotent keyed by `request_id`.
- **اختلاف النقل المحلي والسحابي:** يمنع بوضع العقد في طبقة Sanad protocol المشتركة.
- **فقد الرسائل عند الانهيار:** يمنع بالتخزين الدائم قبل إصدار حالة الانتظار.
- **تلوث سياق LLM ببيانات العرض:** تبقى حالات lifecycle في metadata، ولا تدخل النص المرسل للنموذج.
- **تراجع ترتيب المحادثة:** يثبت باختبارات live/history للترتيب `tool → steer → final`.

## 14. تعريف الاكتمال

تعتبر الخطة مكتملة عندما يصبح الوكيل المصدر الوحيد لحالة الرسائل المعلقة، وتستطيع الواجهة عرض وإلغاء Queue وPending Steer دون تخمين أو حذف تفاؤلي، مع استعادة الحالة بعد إعادة التشغيل، واجتياز اختبارات السباق والترتيب وإعادة الترطيب على النقلين المحلي والسحابي.
